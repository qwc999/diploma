# CRYPTO006 — non_constant_time_compare

## Какая проблема

Правило CRYPTO006 находит сравнение криптографически чувствительных значений через обычные операторы `==` и `!=`. В Python это часто встречается в проверках подписи, HMAC, токена доступа, session token или хеша пароля:

```
received == expected_signature
provided_token != stored_token
mac == expected_mac
password_hash == expected_hash
```

Для таких значений обычное сравнение строк или байтов является небезопасным. Корректная форма — constant-time comparison через стандартные функции `hmac.compare_digest` или `secrets.compare_digest`.

CWE: CWE-208 (Observable Timing Discrepancy).

## Почему это проблема

Обычное сравнение последовательностей обычно завершается после первого отличающегося элемента. Если первые байты совпадают, операция выполняется дольше; если отличие находится в начале, быстрее. Для обычных бизнес-строк это несущественно, но для секретных или проверочных значений такая разница может стать timing side-channel.

В backend-коде риск особенно заметен в функциях проверки:

- подписи webhook или API-запроса;
- HMAC от тела запроса;
- bearer token, session token или API key;
- password hash или digest, используемый как проверочное значение.

Если атакующий может многократно отправлять запросы и измерять время ответа, он получает побочный сигнал о том, насколько длинный префикс переданного значения совпал с ожидаемым. На практике шум сети усложняет атаку, но сам класс ошибки достаточно известен и вынесен в CWE-208.

## Почему это решаем именно мы

Bandit 1.9.4 и Semgrep 1.161.0 с локальным open-source набором `semgrep-rules/python` на финальном корпусе из 6 сценариев не нашли ни одного ожидаемого срабатывания: 0/6 TP, 6 FN, 0 FP на safe-файле у обоих инструментов.

Причина систематическая: проверяемый паттерн не является вызовом опасной функции или небезопасным параметром конкретного API. Это обычный AST-узел `Compare`, который становится криптографически значимым только по контексту имён: `expected_signature`, `provided_token`, `expected_mac`, `password_hash`, `digest`, `hmac_value`.

CRYPTO006 продолжает подход CRYPTO001. Там крипто-контекст по имени переменной повышает severity для слабой генерации случайных значений; здесь похожая идея используется для сравнения криптографических значений. Отличие в том, что глобальный словарь `CRYPTO_NAMES` не расширяется: для CRYPTO006 используется локальный набор имён, специфичный для сравнений, чтобы не изменить поведение уже реализованных правил.

Кейс классифицирован как продвинутый: оба основных аналога полностью пропускают все уязвимые строки.

## Что детектирует правило

Правило обходит AST и ищет узлы:

```
ast.Compare(
    left=...,
    ops=[ast.Eq() или ast.NotEq()],
    comparators=[...]
)
```

В MVP поддерживаются только простые сравнения с одним оператором и одним comparator:

```
a == b
a != b
```

Оба операнда должны быть статически видимыми именами:

- `ast.Name`, например `token`;
- `ast.Attribute`, например `self.token`.

Срабатывание создаётся, если хотя бы одно из имён содержит чувствительный сегмент. Локальный набор CRYPTO006 включает базовые crypto-имена (`token`, `key`, `secret`, `password`, `session_id`, `api_key`) и дополнительные имена для сравнений: `signature`, `sig`, `mac`, `hmac`, `digest`, `hash`, `password_hash`.

Сегментация имени такая же, как в `detect_crypto_name`: `expected_signature` матчится по `signature`, `provided_token` — по `token`, `password_hash` — по полному имени или по сегментам `password` / `hash`.

Severity всегда `high`, потому что обычное сравнение криптографического проверочного значения является прямым нарушением, а не слабым подозрением.

## Безопасная альтернатива и ограничения MVP

Безопасная альтернатива:

```
hmac.compare_digest(received, expected_signature)
secrets.compare_digest(mac, expected_mac)
not hmac.compare_digest(provided_token, stored_token)
```

В `safe.py` корпус зеркально покрывает все 6 уязвимых сценариев через `hmac.compare_digest` и `secrets.compare_digest`. Дополнительно добавлены негативные примеры обычных сравнений статуса и чисел, чтобы правило не флаговало не-криптографические `==` / `!=`.

Ограничения MVP:

- цепочки сравнений вроде `a == b == c` пропускаются;
- сравнения результата вызова функции, например `get_token() == expected`, пропускаются;
- dataflow не выполняется: `x = token; x == expected_token` не связывается с исходным `token`;
- сложные выражения, индексация и вычисленные значения не анализируются, если имя не видно как `Name` или `Attribute`;
- кастомные wrapper-функции вокруг `compare_digest` не распознаются;
- сегмент `mac` трактуется как криптографический Message Authentication Code. Сетевые адреса вида `mac_address` являются неоднозначной зоной для будущих уточнений, поэтому такой пример не включён в safe-корпус.
